段階2の実行計画。**現在は未許可。** ユーザーによる `prediction.md` と `prediction.lock.json` を含むcommit・pushの確認と、別タスクでの明示的な実行許可が両方そろうまで開始しない。ネットワーク利用は計画に含めない。ローカル時刻やlockだけを承認・pushの証拠にしない。

対象は `selection.csv` の40問、元DSL＋5変換、seed=380101,380102,380103、各180秒、各1コア。主比較は720実行。さらに元DSLを同じ3 seedで各1回だけ繰り返す対照120実行をあらかじめ加え、計840実行に固定する。元DSLの再実行も新規solver実行なので段階2まで禁止。過去の元DSL結果を代用しない。途中の正答率を見て延長・seed追加・問題交換をしない。

まずユーザーが固定したcommitのクリーンなチェックアウトを用意する。現在の作業コピーには別作業の未追跡ファイルがあるため、そのまま本計測に使わない。`--allow-dirty` は使わない。`src/`、runner、コーパス、依存lockが60db4b6と一致し、prediction lockの全ファイルSHAが一致することを読むだけで確認する。承認commit、pushの確認方法、チェックアウトcommit、機械・OS・CPU・Python・依存版・使用した4物理コアをreceiptに残す。依存環境は既存のオフライン環境から準備し、runnerの `runtime_fingerprint` とengine lock検査を通す。不足があれば止める。環境差を黙認して続けない。

`execution-plan.json` に210 batchの順を固定した。IDをSHA-256(`Q38/blocks/v1|<id>`)順に4問ずつ10ブロックにし、各ブロック×seed内で7modeをSHA-256(`Q38/schedule/v1/<block>/<seed>|<mode>`)順に実施する。時間帯・順番の偏りを弱めるための順序であり、完全な均衡は保証しない。原本反復は原本と**同じファイル・同じID・同じseed**を使い、出力先だけを変える。

1 batch = 4問×1mode×1seed。`benchmarks.research_runner run ... --jobs 4` を1本ずつ動かす。同時に複数batchを始めない。runner自身の物理コア選択・affinityと1thread設定を使用し、全体でも最大4実行・4コア。`PYTHONHASHSEED=0` も固定し、複数機械や丸めモードを混ぜない。1子プロセスは180秒予算、runnerの外部watchdogは188秒。各runコマンドは1波なので約188秒＋検証・起動分、通常4分以内。batchをまとめる長時間シェルコマンドは作らない。

生成したargvの `<verified-python3.12>` と `<external-results-root>` は、許可後にreceiptで絶対パスを確定する。run結果はチェックアウト外へ一時保存し、全batch・採点が終わってから指定フォルダの `results/` へ移す。これでrunnerの「クリーンなGit作業木」条件を後続batchでも守る。入力DSLはmodeごとの `inputs/<mode>/cases.jsonl` と `dsl/` を使い、埋込みDSLとファイルの一致もrunnerで確認する。

Linuxの `prlimit --fsize=4900000:4900000 -- ...` をrun・assess・summarizeに共通適用し、各出力ファイルを5,000,000 bytes未満に制限する。上限・クラッシュ・契約違反が出たbatchは理由を保存し、成功扱い・黙った再試行はしない。batch別の小さなJSON/JSONL/CSVを保存し、全ログを単一ファイルへ結合しない。異常停止で成果物が欠ければ主集計を未完として報告し、同じ予測のまま追加実行するかは別に確認する。

採点は各batchについて、**変更しない `benchmarks.research_runner.assess_campaign`（CLIのassess）とsummarize**を使う。参照答えは元コーパスからコピーし、実行時にsolverへ渡さない。元のID・target・答えの形式を維持しており、特別な答え変換は足さない。`matched`（正常終了かつ厳密答え集合の完全一致）を唯一の正解指標にする。答えなし、余分な根、欠けた根、runtime不正を勝手に正解へ再分類しない。

問題i、mode vの正答率を `S(i,v)=matchedの和/3` とする。「正答率の大差」Aは、5変換のどれかで `|S(i,v)-S(i,original)| >= 2/3` となる問題。主たる割合の分母は固定40問。少数seedの観測差であり、母成功確率の差を推定できたとは言わない。全mode×seedの対応表、1/3差の数、正誤が食い違うseed数も出す。

「時間の大差」Tは、ある同じ変換について、**両方matchedの対応seedが2個以上あり、そのうち少なくとも2個で同じ方向の3倍以上、かつ2秒以上の差**が出る問題。時間はassessmentの `wall_seconds`。欠測・0以下・非有限値のpairは判定不能。3個目の方向も隠さず出す。十分な成功pairがない問題は時間判定不能と明記し、失敗を速い解答として扱わない。T/40と、時間比較可能問だけを分母とした割合を併記する。副指標は成功時 `min(wall_seconds,180)`、失敗時180とした費用と、seedごとの時間比。

同じ定義を `original_repeat` 対 `original` に適用し、AとTの背景変動を測る。変換と同程度の変動が原本反復にも出た場合、変換の因果効果とは結論しない。正解の改善と悪化を分け、5比較の最大を取ることによる偶然差も明記する。p値による40問の有意差認定は行わない。問題単位の全件表と8層別の件数を中心に報告する。

原因については保存されたcounters、phase timings、採用元、尺度座標のdiagnosticsを対応付けるだけとする。点名だけ・変数順だけ・条件順だけと複合の比較で、どの変更が差を生んだかを絞る。作図順は介入しない。尺度軸の変更が観測されても全差をそれで説明したとはしない。始点の対応・NOMADの方向列・丸め誤差の直接追跡が既存出力に無ければ未同定と書く。始点を揃える追加介入やQ34の再実行はこの計画に含めない。

費用上限は本比較720×180秒=36 core時間、対照を含め840×180秒=42 core時間。4コアで理想的に10.5時間、全件が188秒watchdogまで達すれば約10時間58分＋検証・採点。余裕込みで半日を確保する。平均10秒なら約35分、30秒なら約1時間45分という計算は参考値で、対象40問の新規実測による見積りではない。実測なしに短時間完了を約束しない。
