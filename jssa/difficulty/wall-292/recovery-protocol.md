# 保存不整合・プロセス停止後の再開手順（再開計算前に固定）

2026-10-23。初回プロセスは終了コード1で終了し、run-complete.jsonは作られなかった。確認可能な完了サマリーは127問。残ったrun.logは途中までで、終了理由は特定できない。完了サマリーがあるのに開始点ログがprefixのみになった保存不整合もある。複数のmtimeが成果物編集中の時刻と一致するが、原因は確定していない。

科学的な条件・予測・判定基準はpreregistration.mdのまま。run.py・g2.py・src・manifestは変更しない。以下は保存と中断処理のみの修正であり、結果を良くするための再試行ではない。

1. 現存する初回の全問題サマリー、progress、run.log、不足ログのprefixを別名保存する。初回に完了したことが確実な開始点数、現存する完全な開始点行数、欠落kをrecovery-plan.jsonに固定する。少なくとも実施された初回の呼出し数を計算する。中断直前の未記録呼出し数は不明として残し、正確な総呼出し数を捏造しない。
2. 完全な開始点行が存在する場合はそのまま保持する。欠けた行・未実行の行だけを、同じ保存座標、同じarm順、同じ予算・採点器で補う。既存行を都合の良い再実行に置き換えない。
3. 実際の計算は凍結したrun.solveを呼ぶ。1問ごとに別プロセスを使い、同時の計算プロセスは最大4。長時間開いたままのappendファイルをやめ、各開始点が終了するごとに完全なprefixを一時ファイルからatomic replaceする。問題終了時に別名のcompleted-recordsにも完全なログを一度保存する。
4. 各armの開始直前・終了直後に再開用stateを保存する。新プロセスがarm途中で終了した場合、そのarmはerrorと記録し同じarmを再試行しない。他の未実施armを続けるためのプロセス再起動は1問につき1回まで。2回目もプロセスが終了した場合、残る未実行armはmissing_run（主集計では失敗）とする。終了コード・標準エラーは個別保存する。
5. 初回完了サマリーがある問題では、復元後のB/N/G2の分類数を初回と比較する。一致しても、失われた各終点座標・軌道まで初回と一致したとは主張しない。異なる場合も隠さず記録する。主集計は完成した開始点行に基づく一組のデータに固定し、初回の集計値も感度分析として残す。どちらが好結果かで選択しない。主要予測の成否が復元前後で変わる場合は不安定と明示する。
6. 補完した行は出所を明記し、独立した反復として二重計上しない。初回と再開後の費用が混在すること、初回の一部軌道・時間は失われたこと、追加の計算回数、現在残る欠測を報告する。

この手順は再開後の新しい局所探索より前に保存する。登録の閾値・G2係数・開始点選択は変えない。
