# 事前登録4・版B（LM法を1段目にした版、LM_FIRST=1）：Windows PC での 150問×3seed×2条件＝900実行

## 条件
- 実行環境：Windows 11（Ryzen AI 9 HX 370）、Python 3.12.11、PyNomad 4.5.1。`uv sync --frozen` で凍結版（60db4b6）の依存を入れた別の clone（`C:\jssa-redraw`、branch 580428e）。solver 本体は変更なし。
- 検証用の改変：`LM_FIRST=1`（1段目の探索を disco_mads から scipy_multistart に替える、事前登録4の版B）と、選び直し（redraw）のパッチ（`patch/`）。凍結版の本計測とは別物です。
- seed 101〜103、180秒、1コア、並列6。各実行は論理CPU 0,2,4,6,8,10（`CPU_STRIDE=2`、SMT の兄弟を避けて6つの物理コア。兄弟が0/1の並びは未検証）に固定。条件（plain/redraw）は問題ごとに順序を入れ替えて交互に実行。
- 負荷の記録：Windows には `os.getloadavg` がないため、`cpu_percent_start` は開始時の CPU 使用率（%）です（中央値 30.1%、最大 78.9%）。Linux の loadavg とは単位が違います。この間、別のキャンペーンが WSL の物理コア6〜11で動いた時間があります（実験2、03:14〜04:07）。
- 実行は2回に分かれました。1回目（18:53〜01:05）で、Windows 固有の問題により36実行が記録されず、さらに 01:05 にキャンペーンのプロセスが（原因不明のまま）消えて約2時間止まっていました。03:17 に修正版で再開し、04:23 に900実行すべてが記録されました。

## 修正点（`campaign_winpc_patched.py`、凍結版 solver・条件・採点は不変）
1. solver の出力を utf-8 で読む（cp932 で読めずに失敗していた）。
2. 打ち切り時の `psutil` の例外を許容。
3. solver の出力がない実行を `matched=False, status=no_result` として記録。
4. `solver_result` に `diagnostics` がない実行（redraw 腕の12実行）を `matched=False` として記録し、生の結果を保存。
5. （別の変更）`CPU_STRIDE` 環境変数（既定1、今回2）で、論理CPUを1つおきに使う。

## 結果（`score.txt`、事前登録4の採点器 `score.py`）

| 項目 | 値 |

| 問題数×seed | 150問×3 seed。各条件450実行 |

| A0（参考）：選び直しが一度でも起きた実行の割合 | 0.767（事前登録4の予想「2割未満」は既定版Aの話。版Bの値） |

- redraw 腕には、時間制限を超えた（`solve exceeded its time limit`、181秒前後）実行が5、エンジンが予期せず停止した実行が7あります（12実行、AIME-2018-I-15 の3 seed ほか）。これらは不正解として数えています。plain 腕には同様の実行はありません（plain の不正解18実行はすべて `no_answer_found`）。
- 版Bの結果は、事前登録4が書いた「S1が外れたら、局所探索の成功率の改善は、完成したsolverの費用の改善には移らなかった」に当たります。ただし、redraw 腕で12実行が制限時間・停止で失われていることは、redraw の実装が時間制限と相性が悪い例であり、費用の差の一部を占めています。
