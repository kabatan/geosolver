## 結果

**公開入力36問をすべて実行し、GMBが配置を返したのは32問（88.89%）だった。**
4問は配置なしで正常終了した。時間切れ・異常終了・観測されたCPU制限違反は0件。
論文で表現非対応とされた3問も記録から除外していない。

ここでいう成功は、GMBが数値的な配置を返したことだけを指す。
元の数学問題の証明・求値に成功した、あるいは全条件を独立に検証したという意味ではない。

## 配置生成と結論チェックを分ける

公開入力36問中、32問には結論を調べる`eval`があり、4問にはない。
GMBの既定値どおり`enforce_goals=False`とし、結論を探索条件に加えていない。

配置を返した32問のうち、29問で`eval`が利用可能だった。
その全項目が上流の閾値`eps × 10 = 0.01`以下だったのは**25 / 29問（86.21%）**。
残る4問は以下のとおり。`eval`なしで配置を返した3問は、この率の分母に入れていない。
また、`eval`を持つ全32入力を分母にすれば、「配置生成かつ全eval通過」は25 / 32問（78.13%）となる。
複合的な`eval`は複数の数値チェックへ展開されるため、入力のeval文数と下表の項目数は必ずしも一致しない。

| 配置は生成したが全evalは通過しなかった問題 | 通過項目数 / 全項目数 |
|---|---:|
| IMO 2000 P6 | 1 / 3 |
| IMO 2003 P3 | 3 / 5 |
| IMO 2017 P4 | 0 / 3 |
| IMO 2019 P6 | 0 / 1 |

これはGMB自身が算出した値による診断である。独立な幾何検査器は今回実装していない。
これだけで、失敗の原因を入力の省略・枝選択・数値誤差・実装不具合のいずれかに断定することはできない。
逆に、eval通過例をすべて「正しい図」と認証することもできない。座標と全eval値を保存し、後で再検査できるようにした。

## 配置を返さなかった4問

| 問題 | 時間 | 3試行の終了時loss | 確認できた停止・棄却の経路 |
|---|---:|---|---|
| IMO 2000 P1 | 36.792秒 | 0.000738, 0.000608, 0.000589 | loss閾値は満たしたが、点間距離の受理条件を満たさず |
| IMO 2004 P5 | 11.494秒 | 0.003083, 0.002412, 0.002885 | 3試行とも反復上限までにloss < 0.001とならず |
| IMO 2007 P2 | 21.850秒 | 0.041196, 0.041217, 0.118288 | 同上 |
| IMO 2008 P6 | 115.791秒 | 1.809246, 1.719555, 1.728761 | 同上 |

lossは丸めた表示。元の値は各runの`events.jsonl`に保存。
IMO 2000 P1の距離判定は、3回ともlossを満たしたのにmodelなしで終了したログと、
固定版`TfOptimizer.solve/valid_model`の分岐から特定したもの。
この設定で残る棄却条件は、名前付き点の間隔が`min_dist=0.1`以上かどうかである。
棄却された点対・座標自体は保存していないため、それ以上の幾何的原因は未確定。
4問とも「幾何的に解がない」という結果ではない。失敗後の追加試行・設定調整は行っていない。

## 固定した条件

- GMB公開commit：`f070afe18ed874b3a31db519ea6f593f40a1be00`。sourceファイルの変更なし。
- 計測実装・事前方針のcommit：`77e97a8b431aa9108963b5b037a5f54808a2d74b`。
- Python 3.8.20、TensorFlow 2.7.4、NumPy 1.18.3。全55依存をlockで固定。
- CPU：AMD Ryzen 9 9950X3D、Linux x86-64。GMBの全threadを論理CPU4に固定。
  同じ物理コアのsiblingはCPU20だが、GMBには許可していない。
- 1ジョブずつ、各問1回、seed 0。1回の内部で10初期値・最大3試行・各5000反復という上流の既定値を維持。
  上限180秒、GPU無効、TensorFlow/BLASの計算thread数1。
- 実行時にgraph内の乱数seed、時刻、座標保存用のhookを追加した。探索更新や追加のTensorFlow評価は行っていない。
  記録の費用も実行時間に含む。人工入力ではhookあり／なしのmodel JSON全体が一致した。
- 観測したGMBのOS thread数は最大5だが、すべての観測affinityは`[4]`のみ。
  runtime threadが複数存在することと、複数CPUで並列計算することは区別した。
  process終了時に残っていた所有子孫processは0件。監視controllerの資源はGMBのCPU/RSS値には加算していない。
- CPUを占有して他の作業を停止する措置は行っていない。governorは`performance`、boostは有効。
  背景負荷・CPU時間・周波数・メモリ状況を実行前後に記録した。独占・無負荷環境とは主張しない。

入力36ファイルは固定版の`problems/IMO/*.smt2`とbyte単位で一致する。
非対応3問のIDは、論文に掲載された明示的な一覧ではなく、公開入力と問題文から照合・再構成した
IMO 2002 P6、2006 P6、2011 P2であり、著者に確認したものではない。
この3行は実行せず、時間も0ではなく欠測値として扱った。根拠は[事前方針](PROTOCOL.md)を参照。

## 証跡と再検査

全rawデータの作業用保存先：
`/home/kabatan/work/solver/benchmarks/local-evaluation/gmb-imo39-seed0-cpu4-20260831/`。

- `inputs/`：実行した36入力。
- `runs/<case>/0/`：request、stdout/stderr、時刻付きevents、実行identity、CPU・RSS・終了状態。
- 各runの`models/000.json`：返された32配置の点・直線・円・結論チェック等。
- `validation/`：実行前の303件の全試験結果（failure/error/skip 0件）と人工入力での確認記録。
- `SHA256SUMS`：報告書も含めた全ファイルのSHA-256一覧。rawデータは上書きしない。

Gitには報告書・manifest・CSV/JSONL・summary・checksum一覧を保存する。
raw一式は上記directoryに加え、repo外の研究資産directoryにもarchiveとして保存する。
archiveの場所・hashはGit側の`ARCHIVE.md`に記す。Gitだけで全座標・ログが得られるわけではない。

```bash
.venv/bin/python -m benchmarks.gmb.campaign verify benchmarks/local-evaluation/gmb-imo39-seed0-cpu4-20260831
```

この検査はchecksumとJSON集計の再生成一致を確認する。CSVと元データの行単位の一致、
入力hash、model数、model内のeval値からの再集計も別途確認した。
checksumは保存後の変更検出の手段であり、第三者による実験認証ではない。

## この結果の使い方

この値は「このPC・この公開入力・このseed・この依存版」での基準値である。
単一seedなので安定性や成功確率の精密な推定はできない。
[原論文v2 §4](https://arxiv.org/html/2012.02590v2)の3反復とは回数・環境・計時範囲が異なるため、
論文掲載の平均時間から速度向上率を計算しない。

GeoSolverとの比較には、同じ幾何条件を与えた入力と共通の独立検査器が必要である。
今回の32 / 36をGeoSolverの既存323問の厳密求値成功率と直接比較しない。
本作業ではGeoSolver本体・依存lock・323問のDSL/参照値・`solver-a0`を変更していない。
