# Frozen short-answer scoring audit

Static, read-only audit of `PROTOCOL.md`, `score_fit.py`, `run_study.py`, the frozen job/key schema, and the unchanged greedy driver. No model output, GPU job, or scorer execution was used. The three inspected files match their SHA-256 entries in `freeze.json`.

## Finding

**Conditional gate mismatch in the initial frozen scorer (resolved below).** The protocol requires all four arms' 30 reserved-shape answers to finish naturally before either transfer gate may open (`PROTOCOL.md:29`). Initially, `score_fit.py:68` checked that the `length`, `unparsed`, and `nonpositive` counts were zero, but did not check that every model row had `finish_reason == 'stop'`. An answer with another finish reason and a parseable positive number could have passed `eligible`, allowing a gate to open. The score summary's `correct` count already required `stop` (`score_fit.py:12`), so this mainly affected the log-error gate. Parent was notified before this note was written.

## Checks that match the protocol

- **True value versus shuffled label.** Every arm is scored against `fit-answer-key.json`'s true `answer_exact` (`score_fit.py:34–46`). For 80 trained rows only, the delivered shuffled target is recorded separately as a memory side measure (`:49–52,77`). The answer-free jobs contain no `target` or `answer_exact`; the key's 80 trained targets equal the original correct training targets, and all 80 shuffled targets differ.
- **Numerical rule.** Finite parsed values use absolute error `≤ 1e-4` or relative error `≤ 1e-5`; relative error and positive-only absolute log ratio are recorded (`score_fit.py:35–47`). Missing, nonpositive, and length outcomes are counted separately (`:9–18`). Correctness counts only natural `stop` responses (`:12`). The parser is the frozen prior parser in `related-numeric-sft-2026-09-28/analyze.py`, ultimately using `qwen/answer_check.py` for finite expressions.
- **Four arms and 30 reserved shapes.** `run_study.py:18–21,63` uses base, correct128, correct512, and shuffled512 on the same `fit-jobs.json`. It has 110 unique jobs: 80 `trained_all` and 30 `reserved_shape`, with reserved variants 10–12 for every source. The scorer expects 440 rows (`score_fit.py:29–54`), summarizes each split and source (`:64–67`), and compares a per-source median calculated from the eight original training targets (`:23–27,55–66`). The shuffled arm has the same within-source target multiset, so the constant predictor is common to both label conditions.
- **Common budget extension.** Initial cap/context are 32768/40960. If *any* arm has `finish_reason == 'length'` for a job, `run_study.py:64–71` regenerates that job for *all four* arms at 81920/98304, then, if still length in any arm, at 131072/147456. `score_fit.py:31–33` selects the same final cap per job for all arms. The unchanged `generate_greedy.py:40,51–53,68–76` fixes batch size 4, temperature 0, top-p 1, top-k −1, presence penalty 0, and per-job seed.
- **Prospective transfer gate.** Subject to eligibility, correct512 must beat the maximum precision count of base/correct128/shuffled512 by at least 3 (`score_fit.py:69–70`), or have mean absolute log ratio at most 80% of each of those arms and the median predictor, with strict wins over shuffled512 and the median predictor on at least 7 of 10 sources (`:71–76`). This matches `PROTOCOL.md:29–32`. The driver stops after writing the gate; the optional long-form transfer phase would require a separate run if it opens (`run_study.py:72–75`).

The audit does not assess mathematical validity of any generated explanation or inspect actual response values. I changed no source or scoring file.

## Amendment verification

After the finding was reported and before evaluation generation, the parent amended `score_fit.py:68` to require `all(r['finish_reason']=='stop' for r in rows if r['split']=='reserved_shape')` in addition to the existing eligibility conditions. This covers the four arms' 120 reserved-shape rows and closes the identified gap. I confirmed the updated scorer's SHA-256 is `dbe11c05789269107e604267524efb4114c592937e6a0d991d5dc966455d6063`, matching the updated `freeze.json`; `PROTOCOL.md` and `run_study.py` remain at their prior frozen hashes. The parent preserved the prior freeze as `pre-scorer-amendment-freeze.json` and documented the change in `SCORER_AMENDMENT.md`. No further protocol mismatch was found in the requested scoring and gate logic.
