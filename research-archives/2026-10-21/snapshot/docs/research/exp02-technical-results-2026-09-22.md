## 確認できた問題と採用した修正

旧TRL→Liger経路はglobalな有効トークン分母を渡さず、外側で累積回数による除算もしていた。
長さの異なる回答を、今回意図したtoken単位の目的関数として重み付けしていなかった。
生成への同期はBF16のbaseにLoRAをmerge/unmergeする方式だった。

今回、学習側の分母・累積・optimizer stepを明示した小さいrunnerに切り替えた。
既存のTRL 0.26.2とvLLM 0.29.0の互換shimをさらに増やす方式は採らず、生成・更新を別processで実行する。
Ligerは参照実装として照合に残し、実運用では同じ勾配を与えるtoken方向の分割計算を使う。
凍結LM headの不要な勾配と、回答長×全語彙の巨大な中間logitsを確保しない。

採用する目的関数は

\[
 L=-\frac{1}{N}\sum_{i,t}m_{it}\min\{r_{it}A_i,\operatorname{clip}(r_{it},0.8,1.2)A_i\},\quad
 A_i=R_i-\overline R_{\mathrm{group}},\quad N=\sum_{i,t}m_{it}.
\]

打ち切り回答のmaskを0にした後のNを、同じoptimizer更新の全micro-batchで共有する。
それぞれのbackwardを足し合わせ、さらにmicro-batch数で割ることはしない。KLは0。

## A：損失・勾配

長さ2/6、長さの異なる16回答、micro-batch 1/2/4/16、padding、打ち切りmask、全mask、ゼロadvantage、clipping内外、正負のadvantageを検査した。
CPUの44比較はすべて通過し、最大相対勾配誤差は **3.47×10⁻⁷**。
分母の基準と独立に、通常のdense autogradを参照としている。

## B：adapterの変化が推論に届くか

H01・H02・DA05・DB02の固定入力、末尾32位置ずつを比較した。
HF側では全語彙logitsと指定tokenのlogprob、vLLMでは指定tokenのlogprobを保存した。
下表は**baseからの変化ベクトル**の比較であり、logits全体がほぼ同じというだけの比較ではない。

| exp01 adapterの経路 | 指定token logprob変化の相対L2誤差 | cosine |
|---|---:|---:|
| HF FP32 mergeとFP32未mergeの比較 | 0.118% | 0.9999993 |
| BF16未mergeとFP32参照の比較 | 963.6% | 0.110 |
| exp01 BF16 mergedとFP32参照の比較 | 1176.7% | −0.446 |
| FP32 actor、Tritonの既定TF32計算 | 47.2% | 0.909 |
| **FP32 actor、Triton IEEE、FP32 KV** | **0.275%** | **0.9999962** |
| FP32 actor、IEEE、FP16 KV | 44.6% | 0.902 |

既定TF32/FP16 KVでは同一入力の繰り返しでも差が出た。採用したFP32/IEEE/FP32 KVでは再実行差0、baseのHF対vLLMの指定logprob最大差6.68×10⁻⁵。
元のadapterによるFP32参照のlogprob差RMSは0.01029。
今回の入力・微小な更新ではBF16の未mergeだけでも十分でなく、計算精度とKVも揃える必要があった。

これはBF16学習一般が無効という結論ではない。またexp01の不改善の原因を、この比較だけで一つに断定しない。
exp01の実際のtraining baseにはmerge/unmergeを繰り返していた可能性もあり、保存されたadapterだけから訓練中の全状態を復元した比較ではない。

試行錯誤も保存した。vLLMのnative LoRAはこの環境でFP32 weightを受け付けず、FP16 adapterとFP32 activationの組合せもkernelのdtype検査で失敗した。
そのため、不変のbase＋adapterをCPUでFP32 mergeしてactorへ一括ロードする方式を採った。learner自体をmerge/unmergeしない。

## C：固定した短い回答での更新

4問について正解2本・誤答2本、計16本・有効168tokenを固定し、新規LoRAを3更新した。
学習率は1e−6のままで、診断用の学習率増加は行っていない。

- ゼロadapterと無効化したadapterの指定logprob差：0。
- 実モデルでdense経路と採用した分割経路の勾配相対誤差：7.88×10⁻⁶。
- 同じ実モデルでLigerとの相対誤差：3.55×10⁻⁵、cosine 0.9999999994。
- 固定した旧logprobに対する目的関数：0 → 0.003226 → 0.005072 → **0.006991**。
- adapterパラメータ差のL2 norm：0.01651。実行24.5秒、ピークGPU確保18.69GiB。
- 保存・再読込後の差0。新adapterのactorへの反映はFP32参照に対して相対誤差0.0734%、cosine 0.9999997、再実行差0。

CPUの厳密なloss比較の基準1e−5は変更していない。実モデルのGPU比較はLigerとの誤差3.55×10⁻⁵で最初のassertに失敗したため、36層を通る数値計算の順序差として別に記録し、実モデル比較の工学的許容値を1e−4とした。最初の失敗ログも保持する。
採用した分割経路自体は、このGPU比較でも元の1e−5を満たす。

**この人工的な短答への更新は、幾何能力の獲得やon-policy学習の証拠ではない。**

## D：通常の思考を許す実更新

4問×4回答、回答上限約32k。Cのadapterを引き継がずbaseから別に開始した。

| 配置 | 正解数 | 生成時間 |
|---|---:|---:|
| H02 | 4/4 | 750秒 |
| DB02 | 1/4 | 599秒 |
| H01 | 4/4 | 408秒 |
| DA05 | 2/4 | 773秒 |

全16回答が自然終了し、計249,317 token、生成2,529秒（42.2分）、平均98.6 token/秒。
2群が正誤混在し、8回答が非ゼロadvantageを持つ。数値正解11件を全件確認した。
全件が座標計算を中心とする答案で、うちH01の1件には「一般の不等辺三角形で垂心が中線上にある」という偽の主張があった。
数値の正誤判定そのものは正しく、他にも最終答案の核心計算を省略した例がある。
従って、数値報酬の改善を証明能力の改善として集計してはいけない。

最初の実更新は、FP32 SDPAのGQA指定が巨大な注意行列を作るmath kernelに落ち、25GiBを追加確保しようとしてOOMになった。
optimizer更新前の失敗であり、生成済み回答を変えずに、KV headを明示的に展開してEFFICIENT_ATTENTIONを使う経路へ修正した。
128/1,024 tokenで元の密な計算との出力・勾配を比較し、最大相対誤差は1.10×10⁻⁶。
注意機構単独の32,768 token逆伝播も有限勾配で通過した。
Cも新しい注意計算で再実施し、採用経路の勾配相対誤差8.83×10⁻⁶、Liger 3.64×10⁻⁵、目的関数0→0.006991を再確認した。

この変更前後のソースは別々に保存し、`update_recovery_manifest.json` に原因・元manifest・同一rolloutのhashを記録した。
最初の失敗ログとmanifestを成功したものへ書き換えていない。

修正後、同じ16回答で**1回の実optimizer更新が完了**した。

| 確認項目 | 実測 |
|---|---:|
| 正規化分母 | 249,317有効token |
| 非ゼロadvantageの回答 | 8/16 |
| 更新前の勾配norm | 0.0139036、有限 |
| adapterパラメータ差L2 | 0.00562944 |
| 同じ回答群の目的関数 | −0.01087170 → −0.01083136 |
| forward/backward | 233.2秒 |
| 更新処理全体（更新後の再測定・保存含む） | 295.7秒 |
| 更新時ピークGPU確保 | 23.39GiB |
| 長文の生成側／学習側logprob最大差 | 1.15×10⁻⁴ |
| 保存後の再読込logprob差（8回答×32位置） | 0 |
| optimizer復元差 | 0（504parameter、step=1） |

負の値からでも目的関数は改善している。群平均advantageが0でも回答長が異なるため、token正規化した更新前の目的関数が0になる必要はない。
H01は全員正解のため全advantageが0であり、上述の偽の記述を含む回答も今回の更新には寄与していない。
全回答は更新前に生成したもので、11/16という正答数を学習後の改善として扱わない。

さらに、実際のadapterとAdam状態を読み込んだまま、総長32,768 tokenの入力でモデル全体の逆伝播を実施した。
ピークGPU確保27.71GiB、82.1秒、有限勾配で完了した。これは長文回答を反復して作ったメモリ負荷fixtureであり、追加のoptimizer更新や研究用データとして数えない。

今回の実更新で得たadapterもactorへ同期して測定した。
FP32参照の更新差RMSは0.001471、actor側との変化ベクトルの相対誤差は**1.86%**、cosineは**0.999828**で通過した。
このadapterでは同一入力の再実行最大差9.92×10⁻⁵が観測されたため、完全に決定的とは主張しない。
更新差RMSはその最大差の14.8倍で、計画の10倍基準を満たす。

## 所要時間・保存・検証

Dの生成42.2分＋成功した更新4.9分で、主要な実負荷は約47分だった。
失敗を含むGPU試験はJST 04:49ごろ〜05:59に実施した。間の実装作業・GPUが空いていた時間まで全て含めても約1.2 GPU時間相当の上限で、計画の3 GPU時間以内に収まる。
厳密なGPU利用率の時間積分は採っていないので、47分を較正全体の課金時間と解釈しない。

実checkpointを複製した再開試験では、runnerが生成・更新workerを起動せず完了済みラウンドを読み飛ばし、adapterとoptimizerのhashが一致することも確認した。
関連テスト44件が通過し、Ruff検査も通過した。exp01退避manifestの23パスを検証し、元の実験出力6ファイルはhashが変わっていない。
較正の失敗・修正前ソース・全token列・old/new logprob・adapter・optimizerは`.runtime`に保持し、軽い数値資料をdocs側にも保存した。
