## Freeze, branch, and novelty checks

- The nine jobs have nine unique seeds; each seed differs from the corresponding fresh1 and fresh2 seed. The target/control split is exactly H03/H04/H08/H14/H15 versus H01/H02/H07/H13.
- All nine English problems match their grader-only key text, contain no Japanese script, and include no answer. I found no answer-key text in the model-facing messages.
- I compared same-ID complete givens and canonical/English problem texts against v0–v3 and both earlier frozen numeric sets; there were no collisions. The visible novelty givens are outside the original finite parameter projections: H03 `OH=12`; H04 `BC=12`; H08 `AP²=29` (original parameter maximum is 25); H14 `AH=19/3` (also absent when enumerating the original acute parameter tuples); H15 `AB=10`; H01 `BC=28`; H02 `BC=30`; H07 `AB=11`; H13 `BC=11`.
- SHA-256 values for the listed frozen job, key, split, protocol, and construction-check files match `hashes.json`.

## Interpretation and caveats

All nine answer keys and the selected construction branches check out. H02 uses the conventional segment meaning of “on BC”; if a reader instead interprets it as the whole line, the wording would admit extra signed locations for `D1,D2`, so that convention should be explicit in grader notes. The actual selected points are strictly inside the segment.

Fresh3 is a **result-informed supplementary diagnostic**, created after earlier base-retention results were seen. It reuses the same nine source IDs and relation families as fresh1/fresh2, with new numeric instances and one designated visible novelty value per item. It can help check whether a later 50-row condition is stable across numeric refreshes, but it is not an independent geometry-family transfer test or a confirmatory result. No model performance conclusion follows from this input audit.
